HTTP on the Wire

All three versions use the same methods, headers and status codes. What changed is how those messages travel: as text on a connection of their own, then as binary frames sharing one TCP connection, then as independent streams on QUIC over UDP.

01 · Connection setup

Getting to the first byte

Before any HTTP moves, client and server must open a connection and agree on encryption keys. Each round trip (RTT) is a full trip across the network and back: about 20 ms within a city, 150 ms or more across an ocean.

TCP needs one round trip for its handshake. TLS 1.2 then needs two more, and TLS 1.3 cut that to one. QUIC does the transport and TLS 1.3 handshakes together in a single round trip. When the client has visited the server before, it can send the request in its very first packet.

02 · Multiplexing

Many requests at once

A page is rarely one request. An HTTP/1.1 connection carries one request and response at a time, so browsers open up to six connections per origin and queue everything else. Each extra connection pays for its own handshake, and each request still waits a full round trip for its first byte.

HTTP/2 cuts every message into frames tagged with a stream ID, so one connection carries all the requests at once and the responses interleave. HTTP/3 does the same on QUIC streams, after a shorter handshake.

03 · Head-of-line blocking

When one packet is lost

HTTP/2 removed head-of-line blocking at the HTTP layer, but the problem moved down to TCP. TCP delivers a single ordered byte stream and doesn't know those bytes belong to three different HTTP/2 streams. If one packet is lost, the kernel holds every byte after it until the retransmission arrives.

QUIC does know about streams. A lost packet only stalls the stream whose data it carried.

04 · Header compression

Sending the same headers once

HTTP/1.1 resends every header as plain text on every request, so the same user-agent, cookie and accept lines cost 400 to 800 bytes each time. HTTP/2’s HPACK keeps a table of recent headers at both ends of the connection. A new header is sent once and added to the table, and after that it costs one byte.

HTTP/3 uses QPACK, which works the same way but is redesigned so that streams arriving out of order cannot block each other while their headers are decoded.

05 · Connection migration

Walking out of Wi-Fi range

The kernel identifies a TCP connection by four values: source IP, source port, destination IP and destination port. When a phone moves from Wi-Fi to cellular, its IP address changes and the old connection is gone. The app has to open a new connection, handshake again and repeat the request.

QUIC identifies a connection by a connection ID carried in every packet. The server recognises the same connection arriving from a new address, checks that the new path works and carries on.

Version choice

How the browser picks a version

No URL says “HTTP/2”. The browser and server agree on a version during connection setup, and HTTP/3 is something the browser has to discover first.

  1. ALPN inside the TLS handshake. The ClientHello lists the protocols the browser speaks, and the server picks one in its reply. No extra round trip is needed.
    ClientHello  ALPN: h2, http/1.1
ServerHello  ALPN: h2
  2. The server advertises HTTP/3. A response over HTTP/2 includes an Alt-Svc header saying QUIC is available on UDP 443 for the next day.
    alt-svc: h3=":443"; ma=86400
  3. The browser races QUIC against TCP. On later connections it tries QUIC and TCP at the same time. If a firewall drops UDP, it quietly stays on HTTP/2.
  4. Skipping the first-visit penalty. An HTTPS DNS record (RR type 65) can announce h3 before any connection is made, so even the first visit can use HTTP/3.
    shop.example.com. 300 IN HTTPS 1 . alpn="h3,h2"

In practice

What it means for your stack

Your code rarely changes

RFC 9110 defines the semantics for all three versions, so methods, status codes, caching and headers behave the same. Upgrading is usually a setting on the server, CDN or load balancer.

Remove HTTP/1.1 workarounds

Domain sharding spreads traffic over extra connections and undoes multiplexing and header compression. Image sprites and aggressive bundling matter much less than they used to.

Keep HTTP/2 enabled

Some corporate and public networks block or throttle UDP. Browsers fall back to HTTP/2 without telling anyone, so HTTP/3 should be an addition, never a replacement.

Mixed versions per hop are normal

A common setup uses HTTP/2 or HTTP/3 from the browser to the CDN or load balancer, then HTTP/1.1 to the origin. That inner hop has low latency and little loss, so multiplexing gains little there.

QUIC costs CPU

QUIC runs in user space rather than the kernel and costs roughly twice as much CPU per byte as TCP. UDP segmentation offload is narrowing the gap. In return, QUIC improvements ship without a kernel upgrade.

Checking which version you got

Turn on the Protocol column in the DevTools Network tab. From a script, use performance.getEntriesByType('resource')[0].nextHopProtocol. From a terminal, run curl -sI --http3 https://… if your curl was built with HTTP/3.
